一个编辑器窗口能打开，只说明入口已经接通。工具是否好用，还取决于拖动能否取消、两个窗口是否看到同一份数据、关闭后有没有遗留对象，以及保存失败后能否知道哪些内容已经写入。

这个系列从这些具体问题出发，逐步介绍 UE 原生编辑器开发。示例统一称为 **EditorLab**：它编辑一组有连线关系的节点和时间片段，用基础几何体展示结果，不依赖任何游戏规则或专用资源。

## 阅读前先约定三件事

第一，读者需要掌握 C++ 类、继承、模板和基本 UE 对象模型，但不需要已有 Slate 开发经验。遇到框架类型时，先解释它负责什么，再讨论怎样组合。

第二，代码以 **UE 5.3 公开接口**为基线。文章中的代码分为“局部实现”和“伪代码”，均会在代码前标注。它们用于解释机制，不是一套已编译发布的插件；没有提供完整工程的地方，也不会声称复制单个片段就能运行。版本升级时，优先检查实际头文件、模块依赖和函数签名。

第三，本系列是写作草稿。示例经过接口与逻辑审阅，**没有经过原生 UE 插件编译及交互验收**。每篇末尾的操作步骤是读者复现时的验收方法，不是已经执行过的测试记录。博客构建通过只证明文章可以渲染。

## 工具由哪些部分组成

![EditorLab 的职责与数据流：视图发出操作，会话更新文档，预览和保存分别消费结果](/images/ue-editor-series/architecture.svg)

**模块与入口**负责把能力挂到编辑器上。模块注册菜单和 Tab，菜单触发命令，命令打开工具。入口应该很薄：同一个保存动作从按钮、快捷键或脚本触发时，都应进入同一个实现，而不是重复三套逻辑。

**View** 是列表、图、时间轴和视口。它们管理布局、焦点、缩放与鼠标交互，把用户意图转换成明确的操作。视图不应该偷偷维护另一份可保存数据。例如详情面板显示节点名称时应读取文档；用户提交修改时再请求会话更新。

**Document** 保存可编辑内容：稳定 ID、节点名称、连接关系、片段起止时间和基础对象变换。它不关心按钮颜色，也不拥有音频设备。可以先在不启动窗口的情况下测试它的输入校验。

**Session** 管理一次编辑过程：当前选择、历史记录、手势、脏状态、版本号和预览是否需要重建。两个窗口同时编辑同一份文档时，共享会话比彼此复制数据更容易保持一致。窗口关闭和文档释放不是同一事件，最后一个持有者离开后才可能结束会话。

**Preview** 把文档的一份有效状态投射为画面和声音。它是输出，不是数据源。视口里的临时对象被销毁后，应能从文档重新生成；否则重开窗口就可能丢失无法恢复的编辑结果。

**保存与脚本接口**处理外部环境。文件可能被其他程序改动，版本控制可能不可用，Python 参数可能无效。它们应返回具体结果，由界面决定如何呈现，不能用“按钮按下了”代替“保存成功了”。

## 沿着一次拖动理解数据流

假设文档里有一个片段，开始于第 2 秒。用户把它拖到第 3 秒。最小正确流程如下，名称是本文定义的职责，不是引擎内置 API。

```text
按下鼠标 → 命中片段 → 会话记录手势前状态
移动鼠标 → 像素转换为时间 → 校验候选值 → 更新草稿
松开鼠标 → 比较前后状态 → 产生一条撤销记录
取消操作 → 恢复手势前状态 → 不增加撤销记录
点击保存 → 校验文件来源 → 写入 → 回读 → 更新保存基线
```

这里有三个不同的完成点。鼠标移动完成意味着画面更新；松开鼠标意味着一次编辑动作完成；保存完成意味着磁盘已经包含预期数据。把这三件事混为一谈，会产生“每移动一个像素都写文件”“按 Escape 仍然留下撤销记录”或“保存失败却清掉脏标记”等问题。

拖动中需要实时预览，但不必每次重建整个工具。会话可以区分内容版本与预览输入版本。只有影响预览的数据变化时才使预览失效；在列表中换一个选择项，不应该重新加载网格资源。

## 图浏览、编辑内容和播放时间分别管理

点击图节点通常表示“我想查看它”。拖动时间游标表示“我想看到这个时刻”。修改节点名称表示“我要改变文档”。三个动作可以产生关联，但没有理由天然绑定。

EditorLab 将选择 ID、文档内容和播放时间分开。浏览图时允许选择另一个节点，而已准备的时间序列继续保持不变。只有明确的“预览所选内容”动作才准备新序列。这样，用户查阅旁支时不会突然改变当前画面。

这种分离也降低测试复杂度：选择测试只断言选择，文档测试断言数据变化，播放器测试断言时间和采样。若一个点击同时隐式改变三层状态，失败后往往很难找到真正的入口。

## 选工具框架，先看任务

简单的批量资源处理可以从 Editor Utility 或 Python 开始；需要高度定制布局、复杂输入和原生视口时，再投入 Slate C++。这不是能力高低之分，而是维护成本不同。代码量少并不自动意味着边界清晰，反过来，使用 C++ 也不意味着必须手写所有控件。

GraphEditor 提供图视图能力，但不会替你定义源数据和布局策略。自绘时间轴允许精确控制显示和交互，但也要求自己处理命中、缩放、撤销和可访问性。若需求已经包含复杂轨道、关键帧、曲线、绑定和序列资产，应先评估 Sequencer 扩展，而不是逐项复制成熟编辑器。

本系列的自绘时间轴只编辑简单片段；预览视口优先使用隔离的预览世界；保存优先使用单个 JSON 文档。明确限制能使每个例子集中回答一个问题，不必先搭建庞大的框架。

## 怎么判断一层真的完成了

| 证据 | 能说明什么 | 不能替代什么 |
|---|---|---|
| 文档模型单元测试 | 时间区间、撤销、序列化等逻辑符合约定 | 原生输入和画面 |
| 插件编译 | 类型、符号与依赖能够连接 | 运行时对象寿命 |
| 编辑器交互 | 打开、操作、关闭等实际链路可用 | 所有资源与设备组合 |
| 保存后重开 | 磁盘内容可恢复编辑结果 | 写入中断时的恢复能力 |
| 网站构建 | 博客和链接能够生成 | 任何 UE 行为 |

每完成一个部分，先做最小闭环。例如窗口要打开两次、关闭再打开；撤销要跨两个视图操作；保存要改动后写入，再从磁盘构造一份新文档读取。第二次操作经常比第一次更容易暴露持有关系和状态重置问题。
